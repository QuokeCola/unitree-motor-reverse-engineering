Notice

This guide describes the serial protocol spoken by the joint motors of a Unitree G1 humanoid arm, as observed on the wire. It was written without access to any manufacturer documentation for these motors. Every statement is marked by how it was established: verified means it was checked against captured traffic or reproduced on a motor, inferred means it fits the data but was not tested directly, and assumed means it is carried over from Unitree's public GO-M8010-6 motor protocol and not checked on these motors.

The manufacturer may change the protocol in other hardware or firmware versions. Use at your own risk.

Warning

  1. A motor in run mode applies torque as soon as it receives a command with non-zero gains or torque. Keep clear of the joint.
  2. Never connect a second controller to the bus of a complete robot. The onboard controller polls continuously, and two masters on one RS-485 bus corrupt each other's frames. Listening only is safe.
  3. Start with low gains and position targets equal to the measured position. Gains are raw integers with no confirmed physical scale.
  4. Stay inside the mechanical end stops. The motor does not know the joint limits; position is a free-running multi-turn count.
  5. Do not brake a fast joint with a damping command on a bench power supply. It disturbed the supply and latched a fault on every motor on the bus (see "Status Word"). Stop by switching to idle mode.
  6. End stops in counts are not permanent: the position reading can shift by whole output turns after a power cycle or restart.
  7. A motor that is no longer polled keeps applying its last command for 0.5 to 1 s before it drops to idle. Return motors to idle mode before closing the port.

Introduction

Each arm of the G1 carries its joint motors on one RS-485 chain. The controller is the only master. It addresses one motor at a time with a 20-byte command and that motor answers with a 26-byte reply holding its position, velocity, torque, temperatures, bus voltage and a status word. A command carries a complete hybrid setpoint (torque, velocity, position and two gains), so there are no separate enable, mode or parameter messages: everything is expressed in the one command frame.

Field positions for POS, KP and KD were confirmed from the robot's mode changes and by driving the bench motors; T was confirmed as a torque feed-forward on the bench; W was used as a velocity feed-forward with the expected effect. verified

Control law

torque = T + KP × (POS − measured position) + KD × (W − measured velocity)

This is the standard Unitree hybrid command. inferred The individual terms behave as written; the relative scaling of KP and KD in physical units is not known. All fields zero gives zero torque: the joint turns freely.

Mode Values

Each value was tried on one bench motor (ID 4): first with every other field zero, then, for modes 3-5, with small torque, position, velocity and gain commands that move the joint in mode 1, and with a coast-down from speed. verified What distinguishes modes 0, 3 and 5 from each other was not found.

MODEBehaviour
0Idle. Commands are ignored and the joint is passively braked: spun to about 800 velocity counts and switched to this mode, it stopped in about 10 ms. Used by the controller at boot and for scanning.
1Run. Entered on the first frame; the reply reports mode 1. Refused while the status word is non-zero.
2Ignored: the motor stays in mode 0. No motion.
3Accepted (the reply reports mode 3). Torque, velocity, position and gain fields are ignored. Joint braked as in mode 0: stopped in about 10 ms. Torque reading exactly 0 at rest.
4Accepted. Command fields are ignored. Joint free-wheels, the same as mode 1 with an all-zero command: took 25-64 ms to stop from the same speed.
5Accepted. Command fields are ignored. Joint braked as in modes 0 and 3.
6Set position (zeroing), used by the robot's calibration. Needs a specific payload, see "Zero Position"; with an all-zero payload it is ignored and the motor stays in mode 0.
7Restart. One frame is enough, with or without FLAG. The motor answers for about 5 ms, is silent until about 300 ms, then answers again in mode 0 with status 0. Clears a latched fault. The position reading may come back shifted (see "Position After Power-On or Restart").

Sequence Byte

DATA[3] is 0x00 in the first frames after power-on. Once continuous polling starts it changes about every 8 frames (about 6 ms). On three of the five robot motors it alternates between 0x80 and 0x90. On the other two the low bits count up by one at each change while bit 7 toggles. Its purpose is unknown. The bench motors entered run mode and ran normally with the 0x80/0x90 alternation, and also entered run mode with DATA[3] = 0, so no pattern is required for that.

Sending frequency: one reply per command, so it follows the controller (about 1.3 kHz on the robot).
Position: same unit as the command position; it matched the target to within 1-2 counts when holding. verified
Bus voltage: read 24.0-24.5 V on a 24 V bench supply and 47.0-48.5 V on the robot (battery), with brief excursions between 44.5 and 50 V. verified

The reply header is 0xFC 0xEE, and the reply checksum does not cover the header. Both differ from the command, and from Unitree's public GO-M8010-6 protocol (reply header 0xFD 0xEE, 16-bit checksum).

Checksum

CRC-32 with polynomial 0x04C11DB7, initial value 0xFFFFFFFF, no bit reflection and no final XOR. The data is taken as 32-bit little-endian words, each fed most-significant bit first. The result is stored little-endian. This is the crc32_core routine of Unitree's public A1/B1 motor SDK. verified on 3.8 million frames.

uint32_t crc32_core(const uint32_t *words, uint32_t count) {
    uint32_t crc = 0xFFFFFFFF;
    for (uint32_t i = 0; i < count; i++) {
        uint32_t data = words[i];
        for (uint32_t bit = 0x80000000; bit; bit >>= 1) {
            if (crc & 0x80000000) crc = (crc << 1) ^ 0x04C11DB7;
            else                  crc <<= 1;
            if (data & bit)       crc ^= 0x04C11DB7;
        }
    }
    return crc;
}
/* command: crc32_core(frame, 4)       bytes 0-15
   reply:   crc32_core(frame + 2, 5)   bytes 2-21 (copy to aligned memory) */

Operating the Motor

Modes Used by the G1 Controller

The controller never changes the frame type. Robot behaviour is set entirely by the fields of the run-mode command. verified

Power-On Sequence of the Robot

Times are measured from the first frame on the bus, which appeared roughly a minute after the robot was switched on.

TimeControllerMotors
0 s18 frames, 3-4 per motor: DATA[2] = ID, DATA[3] = 0, T = −128, all else 0All answer in mode 0
0-7.0 sSilent-
7.0 sContinuous polling starts, mode 0, all fields 0Mode 0
7.0-7.1 sIDs 2 and 3 only: about 114 frames with a fixed 12-byte pattern in DATA[4]-DATA[15]IDs 2 and 3 switch from a fixed data block to normal telemetry
9.6 sFLAG bit set (0x80 + ID)Mode 0
33.2 sMODE = 1 on all motors in the same round (0x90 + ID)Report mode 1 from the next frame

So enabling a motor means changing MODE from 0 to 1 in the ordinary command; the motor acknowledges in its reply.

IDs 2 and 3 of the observed chain do not report position or temperature until they have received a 12-byte pattern; before that, DATA[3]-DATA[13] of their replies hold a block of data and DATA[14]-DATA[15] read 00 80. This is a challenge and response: after a later restart both the block and the pattern were different. The algorithm is not known, so these two motors cannot be brought up without the robot's controller. The three bench motors (IDs 4, 5, 6) needed no such step.

Enabling a Motor Without the Robot Controller

Sequence used successfully on bench motors IDs 4, 5, 6 at 24 V:

  1. Listen for about 1 s. If any bytes arrive, a controller is present: do not transmit.
  2. Scan: send the idle poll (DATA[2] = ID, everything else 0) to IDs 0-14. Motors present answer in mode 0.
  3. Poll each motor about 20 times with the idle poll.
  4. Poll each motor about 50 times with FLAG set (0x80 + ID), DATA[3] alternating 0x80 / 0x90 every 8 rounds.
  5. Send run-mode commands (0x90 + ID) with all fields 0. The reply then shows mode 1 (on the robot, from the very next frame). The joint is now free.
  6. Command motion by filling POS, W, T, KP, KD. Keep polling every motor in a steady loop.
  7. To stop: send idle polls (MODE 0) until the reply shows mode 0. Idle brakes the joint passively; from top speed the bench joints stopped in 18-27 ms with the supply voltage steady. Do not stop a fast joint with a damping command on a bench supply (see "Status Word").

Steps 3 and 4 copy the order the robot uses but are not required: a motor polled in idle entered run mode on the first frame with MODE = 1, FLAG clear and DATA[3] = 0. verified

If polling stops, a motor stays in run mode for at least 0.5 s and has returned to idle, with status 0, within 1.0 s. It then brakes passively. verified

Status Word

DATA[14]-DATA[17] of the reply are 0 in normal operation. Non-zero values seen:

Value (uint32)Situation
0x00000008Appears when the bus voltage reading falls to about 15 V. Seen on all three bench motors in two ways, both while braking from top speed with a damping command on a 24 V bench supply. With KD 80 the torque reading jumped to 419-689 counts and the voltage fell at once to 15-19 V; the status stayed latched. With a torque-limited brake (about 180 counts) the voltage first rose to 30 V, then collapsed to 10 V about 130 ms later; the motors restarted by themselves when it returned. While the status is set the motor stays in mode 0 and ignores MODE = 1.
0x00040000Robot IDs 2 and 3 for about 0.4 s during boot, with normal operation afterwards.
0x00008000Robot IDs 2 and 3 before they received their 12-byte pattern (these bytes may not be a status word in that state).

0x00000008 is therefore most likely an under-voltage flag, and the damping brakes caused it by disturbing the supply. Switching to idle from the same speed left the voltage at 24.0-24.5 V and the status at 0. The meaning of the other bits is unknown. Clearing a fault: send one frame with MODE = 7 (restart), or switch the motor supply off for about 10 s. These did not clear it: idle polling, run-mode commands, damping commands, the power-on probe frames, and 15 s of silence.

Position After Power-On or Restart

The position reading is multi-turn, but after a power cycle or a restart it can come back shifted by a whole number of output-shaft turns. Seen: 524,288 counts (16 rotor turns) on ID 4 and 819,200 counts (25 rotor turns) on ID 6, in both directions; other restarts shifted nothing. This also gives the reduction ratios of those two joints, 16:1 and 25:1. inferred Because the shift is always a whole output turn, the motor does know the joint's position within one turn: an end stop or zero stored in counts becomes valid again once it is moved by the same whole number of turns. Check this against the reading after every power-on or restart.

Zero Position

The position reading is the joint angle: on the robot's arm chain (IDs 0-4) it is 524,288 counts per output turn (16 × 32,768) with 0 at the joint's zero. verified

The zero is set with MODE = 6. This was captured while the robot ran its own joint calibration; it has not been reproduced with frames of our own. inferred The controller's sequence:

StepFrames
1Press each joint against an end stop: 10 frames per motor about 26 ms apart, DATA[2] = 0x10 + ID (run mode, FLAG clear), T = +16 or −16, KD = 2, everything else 0.
2One frame per motor with DATA[2] = 0x60 + ID, DATA[3] = 0, DATA[4]-DATA[5] = 00 FC, DATA[6]-DATA[9] = the joint angle at that end stop as int32 with 231 = one output turn, and a fixed 6-byte constant in DATA[10]-DATA[15]. The reply reports mode 6.
3One restart frame per motor (0x70 + ID). The motors are silent for about 0.7 s, then answer idle polls.

The five angles sent were +153.00°, +129.00°, +150.00°, −59.99° and +113.00° for IDs 0-4, and at that moment each motor's position reading equalled its angle × 524,288 / 360° to within 0.01 %. The 6-byte constant was the same for all five motors; it is recorded in the lab notes (docs/lab_notes.md), and whether it differs between robots or firmware versions is unknown. Setting a zero is presumably permanent; do not send mode 6 without knowing the joint's true angle.

Without recalibrating, a zero can also be kept in software: store the reading at a known pose and, after each power-on, move the stored value by whole output turns to match the reading.

  • Mode 6: the meaning of DATA[4]-DATA[5] = 00 FC and of the 6-byte constant; reproducing it on a bench motor.
  • Bit meanings of the status word.
  • Purpose of modes 3, 4 and 5, and what separates modes 0, 3 and 5.

  • Reply fields DATA[18]-DATA[21].
  • Whether ID 15 is a broadcast address, and how a motor's ID is assigned.

Software

Drivers implementing this guide accompany it in Python, C++ and MATLAB (g1motor), with the same names in each. In Python:

from g1motor import MotorBus, Joint

with MotorBus() as bus:                    # 6 Mbaud; refuses a busy bus
    print(bus.scan())                      # {4: MotorState(...), ...}
    bus.restart([4])                       # mode 7: clears a latched fault
    bus.set_joint(4, Joint(16, low, high)) # gear ratio, end stops in counts
    bus.enable([4])                        # run mode, zero torque
    target = bus.joint(4).counts(0.5)      # 0.5 rad from zero, at the output
    for _ in range(1000):
        state = bus.command(4, target, 0, 0, 300, 40)
# on exit: back to idle, which brakes the joint
