Notice

This guide explains how to communicate with Unitree G1 arm joint motors over RS-485. It is based on recorded messages and motor tests, without access to the manufacturer's documentation for these G1 motors. Labels show the evidence behind a finding:

  • verified Checked against recorded messages or tested on a motor.
  • inferred Suggested by the data, but not tested directly.
  • assumed Taken from Unitree's public GO-M8010-6 protocol and not yet checked on G1 motors.

The manufacturer may change the protocol in other hardware or firmware versions. Use at your own risk.

Getting Started

To use a driver, read the repository README, then follow the installation steps in the Python, C++ or MATLAB folder. Check the wiring, scan for motor IDs, and try zero torque before a position hold. Scanning sends idle commands; it is not passive monitoring and can interrupt a hold.

Support any load before enabling a motor: run mode with zero torque lets the joint move freely. Idle mode resists motion through passive braking; it does not actively hold a target angle. Keep sending commands to every enabled motor in your control loop.

Terms used in this guide

  • Frame: one group of bytes sent together. A field is one value within it; DATA[0] is the first byte.
  • Polling: sending commands to motors in turn and receiving their replies.
  • Counts: the whole-number values sent in messages, before conversion to angles, speeds or torque. See "Units" for conversions.
  • Rotor and output shaft: the rotor turns inside the motor; the output shaft drives the joint through a gearbox.
  • Gains: control strengths. KP sets the response to position error; KD sets the response to velocity error and provides damping when the velocity target is zero.
  • Feed-forward torque: torque T requested directly, without using position or velocity error.
  • Status word: an integer reporting motor status, normally zero. See "Status Word" for observed non-zero values.

Warning

  1. A motor in run mode applies torque as soon as it receives a command with non-zero gains or torque. Keep clear of the joint.
  2. Never connect a second controller to the bus of a complete robot. The robot controller sends commands continuously. If another controller sends at the same time, their messages collide. Receiving without sending does not cause this conflict.
  3. Start with low gains and position targets equal to the measured position. Gains are protocol integers; their conversion to physical units has not been confirmed.
  4. Stay inside the mechanical end stops. The motor does not know the joint limits; the position count continues across turns rather than returning to zero after each turn.
  5. Do not brake a fast joint with a damping command on a bench power supply. In these tests, this changed the supply voltage enough to leave every motor on the bus in a fault state (see "Status Word"). Stop by switching to idle mode.
  6. Saved end-stop counts may need adjustment after power-off or restart: readings can shift by the count for one or more complete output-shaft turns.
  7. A motor that is no longer polled keeps applying its last command for 0.5 to 1 s before it drops to idle. Return motors to idle mode before closing the port.

Introduction

The joint motors in each G1 arm share one RS-485 communication line, called a bus. One controller sends a 20-byte command to one motor at a time. That motor returns a 26-byte reply containing position, speed, torque, temperatures, supply voltage and status.

Each command includes the working mode, target position, target speed, torque and two gains. The same message format is used to enable a motor, change mode and control motion; these actions do not use separate message types.

Changes in robot behaviour and direct motor tests confirmed which bytes hold POS, KP and KD. Tests also confirmed that T directly adds torque and that W acts as the target speed. verified

Types such as int16 are signed integers and can be negative; uint16 is unsigned and cannot be negative. The number is the bit width. All multi-byte values use little-endian byte order.

How the command controls torque

torque = T + KP × (POS − measured position) + KD × (W − measured velocity)

The command combines three effects, as in Unitree's usual control scheme. inferred

  • T: adds torque directly, without using position or speed error.
  • KP: sets how strongly the motor corrects the difference between target and measured position.
  • KD: sets how strongly the motor corrects the difference between target and measured speed. With a zero speed target, this resists motion (damping).

The formula explains these effects, not how to convert raw counts into N·m. The physical scaling of KP and KD is not fully known. In run mode, setting all command fields to zero gives zero torque and lets the joint turn freely.

Mode Values

Each mode was tested on a separate motor (ID 4), first with all other fields set to zero. For modes 3-5, tests also used small commands that move the joint in mode 1, and checked how it slowed down after switching modes. verified No difference between modes 0, 3 and 5 was identified in these tests.

MODEBehaviour
0Idle. Motion targets are ignored; passive braking resists movement. After running at about 800 velocity counts, the joint stopped in about 10 ms when switched to this mode. Used during startup and scanning.
1Run. The motor enters this mode on the first command and reports mode 1 in its reply. A non-zero status word prevents entry.
2Ignored: the motor stays in mode 0. No motion.
3Accepted (the reply reports mode 3). Torque, velocity, position and gain fields are ignored. Joint braked as in mode 0: stopped in about 10 ms. Torque reading exactly 0 at rest.
4Accepted. Command fields are ignored. The joint moves freely, as in mode 1 with all command fields zero. It took 25-64 ms to stop from the same speed.
5Accepted. Command fields are ignored. Joint braked as in modes 0 and 3.
6Set position (zeroing), used by the robot's calibration. Needs specific data in the command, see "Zero Position". With all data fields zero, the motor ignores it and stays in mode 0.
7Restart. One frame is enough, with or without FLAG. The motor replies for about 5 ms, stops replying until about 300 ms after the restart began, then replies in mode 0 with status 0. Clears a fault that otherwise stays active. The position reading may come back shifted (see "Position After Power-On or Restart").

Sequence Byte

DATA[3] is 0x00 in the first frames after power-on. Once continuous polling starts it changes about every 8 frames (about 6 ms). On three of the five robot motors it alternates between 0x80 and 0x90. On the other two the low bits count up by one at each change while bit 7 switches between set and clear. Its purpose is unknown. The bench motors entered run mode and ran normally with the 0x80/0x90 alternation, and also entered run mode with DATA[3] = 0, so entering run mode did not require a particular sequence.

The reply header is 0xFC 0xEE, and the reply checksum does not cover the header. Both differ from the command, and from Unitree's public GO-M8010-6 protocol (reply header 0xFD 0xEE, 16-bit checksum).

Checksum

The checksum detects damaged messages. Use the exact algorithm below: a general CRC-32 function may use different settings and give a different result.

The settings are polynomial 0x04C11DB7, initial value 0xFFFFFFFF, no bit reflection and no final XOR. Read the bytes as 32-bit little-endian words, then process each word from its highest bit to its lowest bit. Store the result with the lowest-value byte first.

This is Unitree's crc32_core algorithm from the public A1/B1 motor SDK, checked against 3.8 million frames. verified For a reply, copy the covered bytes into aligned memory before calling the function below.

uint32_t crc32_core(const uint32_t *words, uint32_t count) {
    uint32_t crc = 0xFFFFFFFF;
    for (uint32_t i = 0; i < count; i++) {
        uint32_t data = words[i];
        for (uint32_t bit = 0x80000000; bit; bit >>= 1) {
            if (crc & 0x80000000) crc = (crc << 1) ^ 0x04C11DB7;
            else                  crc <<= 1;
            if (data & bit)       crc ^= 0x04C11DB7;
        }
    }
    return crc;
}

Operating the Motor

How the G1 Controller Uses Run Mode

The controller uses the same command format for each behaviour below. In run mode, changing the torque, targets and gains changes what the joint does. verified

Robot stateCommand content
Zero torqueT, W, POS, KP, KD all 0

Locked standingPOS = present position, then gradually changed by the controller toward the standing pose. KP / KD seen on IDs 0-4: 450/10, 300/5, 100/2, 300/5, 20/1

Power-On Sequence of the Robot

Times are measured from the first frame on the bus, which appeared roughly a minute after the robot was switched on.

TimeControllerMotors
0 s18 frames, 3-4 per motor: DATA[2] = ID, DATA[3] = 0, T = −128, all else 0All answer in mode 0
0-7.0 sSilent-
7.0 sContinuous polling starts, mode 0, all fields 0Mode 0
7.0-7.1 sIDs 2 and 3 only: about 114 frames with a fixed 12-byte pattern in DATA[4]-DATA[15]IDs 2 and 3 switch from a fixed data block to normal position, temperature and other readings
9.6 sFLAG bit set (0x80 + ID)Mode 0

So enabling a motor means changing MODE from 0 to 1 in the ordinary command; the motor acknowledges in its reply.

IDs 2 and 3 of the observed chain do not report position or temperature until they have received a 12-byte pattern; before that, DATA[3]-DATA[13] of their replies hold a block of data and DATA[14]-DATA[15] read 00 80. This is a startup check called challenge and response: the motor sends data and the controller returns matching data. Both changed after a later restart. How the controller calculates its reply is unknown, so this project cannot start these two motors without the robot controller. The three bench motors (IDs 4, 5, 6) needed no such step.

Enabling a Motor Without the Robot Controller

Sequence used successfully on bench motors IDs 4, 5, 6 at 24 V:

  1. Listen for about 1 s. If any bytes arrive, a controller is present: do not transmit.
  2. Scan: send the idle poll (DATA[2] = ID, everything else 0) to IDs 0-14. Motors present answer in mode 0.
  3. Poll each motor about 20 times with the idle poll.
  4. Poll each motor about 50 times with FLAG set (0x80 + ID), DATA[3] alternating 0x80 / 0x90 every 8 rounds.
  5. Send run-mode commands (0x90 + ID) with all motion fields 0. The reply then shows mode 1 (on the robot, from the very next frame). The joint is now free.
  6. Command motion by filling POS, W, T, KP, KD. Keep polling every motor in a steady loop.
  7. To stop: send idle polls (MODE 0) until the reply shows mode 0. Idle brakes the joint passively; from top speed the bench joints stopped in 18-27 ms with the supply voltage steady. Do not stop a fast joint with a damping command on a bench supply (see "Status Word").

Steps 3 and 4 copy the order the robot uses but are not required: a motor polled in idle entered run mode on the first frame with MODE = 1, FLAG clear and DATA[3] = 0. verified

If polling stops, a motor stays in run mode for at least 0.5 s and has returned to idle, with status 0, within 1.0 s. It then brakes passively. verified

Status Word

DATA[14]-DATA[17] of the reply are 0 in normal operation. Non-zero values seen:

Value (uint32)Situation
0x00000008Appears when the bus voltage reading falls to about 15 V. Seen on all three bench motors in two ways, both while braking from top speed with a damping command on a 24 V bench supply. With KD 80 the torque reading jumped to 419-689 counts and the voltage fell at once to 15-19 V; the fault stayed active. With a torque-limited brake (about 180 counts) the voltage first rose to 30 V, then collapsed to 10 V about 130 ms later; the motors restarted by themselves when the voltage recovered. While the status is set the motor stays in mode 0 and ignores MODE = 1.
0x00040000Robot IDs 2 and 3 for about 0.4 s during boot, with normal operation afterwards.
0x00008000Robot IDs 2 and 3 before they received their 12-byte pattern (these bytes may not be a status word in that state).

0x00000008 most likely means the supply voltage is too low (under-voltage). Damping while stopping caused large voltage changes. Switching to idle from the same speed kept the voltage at 24.0-24.5 V and the status at 0. The other status bits are not yet understood.

Clearing this fault: send one command with MODE = 7 (restart), or turn the motor supply off for about 10 s. Idle polls, run-mode commands, damping commands, the initial startup messages and 15 s without commands did not clear it.

Position After Power-On or Restart

Position counts continue across turns, but restarting or turning the power off and on can change the reading even when the joint has not moved. The change can equal one or more complete output-shaft turns.

Observed shifts were 524,288 counts (16 rotor turns) on ID 4 and 819,200 counts (25 rotor turns) on ID 6, in either direction. Some restarts caused no shift. These measurements suggest gear ratios of 16:1 and 25:1. inferred

The readings still identify position within one output-shaft turn. Saved end-stop and zero counts need the same whole-turn adjustment as the reading. Check them after every power-on or restart before using them to command motion.

Zero Position

The position reading is the joint angle: on the robot's arm chain (IDs 0-4) it is 524,288 counts per output turn (16 × 32,768) with 0 at the joint's zero. verified

MODE = 6 appears to set the zero position. This was recorded while the robot calibrated its joints; it has not been repeated with commands from this project. inferred The table records what the robot did, rather than a tested calibration procedure for users:

StepFrames
1Press each joint against an end stop: 10 frames per motor about 26 ms apart, DATA[2] = 0x10 + ID (run mode, FLAG clear), T = +16 or −16, KD = 2, everything else 0.
2One frame per motor with DATA[2] = 0x60 + ID, DATA[3] = 0, DATA[4]-DATA[5] = 00 FC, DATA[6]-DATA[9] = the joint angle at that end stop as int32 with 231 = one output turn, and a fixed 6-byte constant in DATA[10]-DATA[15]. The reply reports mode 6.
3One restart frame per motor (0x70 + ID). The motors are silent for about 0.7 s, then answer idle polls.

The five angles sent were +153.00°, +129.00°, +150.00°, −59.99° and +113.00° for IDs 0-4, and at that moment each motor's position reading equalled its angle × 524,288 / 360° to within 0.01 %. The 6-byte constant was the same for all five motors; it is recorded in the lab notes (docs/lab_notes.md), and whether it differs between robots or firmware versions is unknown. The zero setting may be permanent. Do not send mode 6 unless you know the joint's true angle.

Without recalibrating, a zero can also be kept in software: store the reading at a known pose and, after each power-on, add or subtract the count for complete output-shaft turns so the stored value matches the current reading.

To get output-shaft angle or speed, first convert the counts to rotor angle or speed, then divide by the gear ratio. A software zero defines the reference angle. The drivers' units functions handle rotor conversions; Joint handles output-shaft angles and the software zero.

Software

The g1motor drivers implement this protocol in Python, C++ and MATLAB. The three versions use the same API names. This Python example holds one motor at its starting position:

This example enables and continuously commands only ID 4. Scan first and replace the ID with one on your bus. These gains were tested on a separate wrist assembly at 24 V; check their suitability for your joint. On an enabled motor, bus.read() sends zero torque and interrupts a hold; use the state returned by command() instead. A missing or invalid reply returns None.

from g1motor import MotorBus

with MotorBus() as bus:                    # 6 Mbaud; refuses a busy bus
    print(bus.scan())                      # {4: MotorState(...), ...}
    start = bus.enable([4])                # run mode, zero torque
    target = start[4].pos                  # hold the starting position
    for _ in range(1000):
        state = bus.command(4, target, 0, 0, 300, 40)
# on exit: back to idle, which brakes the joint

To work in output-shaft angles, attach a Joint with your gear ratio, measured end stops and software zero. Recheck end stops after every power-on or restart. The torque conversion to N·m is assumed, not measured.
